# harness-engineering

[English](./README.md) | 简体中文

**别再重复贴同一段提示词了。** 这个 skill 先诊断你的编码 agent 为什么时好时坏，再重建它周围的 harness——指令文件、skill、规则、状态、反馈回路与环境锁定。

```
体检（20 条清单）  →  诊断（14 种失效形态）  →  处方（8 组施工法）  →  复检
```

## 它解决什么问题

多数 agent 的失败不是模型失败，而是 harness 失败——只是它表现成了一些你大概已经算在模型头上的现象：

- 同样的事，今天输出好、明天就变差，什么都没改。
- 你已经为某个错误写过规则，它照样再犯。
- 两分钟就说"做好了"，你一抽查，最难的那部分被跳过了。
- `AGENTS.md` 越写越长，agent 反而越来越不听话。
- 昨天还能跑，换台机器就崩。
- 规则确实存在——但只存在于某个人的脑子里。

核心判断是：**harness 就是套在 agent 外面的"操控循环"。** 它决定 agent 在什么上下文里行动、结果如何被检查、检查不过时会发生什么。前馈提高"第一次就做对"的概率，反馈提供"确实做对了"的证据，两者不能互相替代。产出不满意时，要修的是循环里缺失的那一环，不是提示词的措辞。

## 什么时候该用

**该用：**

- 你正在写或改 `AGENTS.md`、`SKILL.md`、原则文档、规则登记表、验收脚本、checkpoint 协议、环境初始化脚本。
- 同一个 agent 任务时好时坏，或同一个错误反复出现，或你正准备往已经过长的规则文件里加第 N 条。
- 一个每周/每天重复的工作流目前还是"每次贴一段提示词"，你想把它变成可复用系统。
- 你在为难以自动化的任务设计验收标准——或者你发现"完成"总是由干活的人自己宣布。

**不该用：**

- 单次、一次性的任务（写封邮件、润色一段话、生成一张图）。不会重复的任务上打磨 harness 不划算，收益不累积。
- 真正卡在模型能力或任务粒度上。先换模型或缩小任务，而不是继续往指令文件里堆规则。
- 具体代码 bug 的定位与修复。那是调试流程，不是 harness 设计。
- 纯文本写作与排版。那是写作类工作，本 skill 不替代它。

## 覆盖范围

skill 内含一份体检清单、14 种失效形态的诊断与处方，以及 8 组施工法。

### 诊断：14 种失效形态

| # | 病症 | 你观察到的现象 | 处方 |
|---|---|---|---|
| 1 | 需求模糊 | 你给一句话，agent 给一个"看起来对、用起来不对"的东西 | **提取指令文件**——约束条件、完成条件、边界情况 |
| 2 | 隐式约定 | 大方向对，细节处处偏差；你总在说"我们这儿不是这么做的" | **建立原则文档**，并写明裁决优先顺序 |
| 3 | 信息散落 | 精准地实现了错误的目标；过时文档比没有文档更危险 | **管理知识依赖**——来源映射 + 定时同步 |
| 4 | 虚假胜利 | 几分钟就说"做好了"，一抽查只做了六成 | **分离执行与验证** |
| 5 | 指令文件腐化 | 规则越多，行为越不可捉摸，你指不出是哪条错了 | **指令文件治理**——登记表、矛盾检测、定期清理 |
| 6 | 前馈痴迷 | 你又补了一条说明，同类错误照旧 | **反馈优先**——写检查，而不是写过程规则 |
| 7 | 反馈过载 | agent 改好这条破坏那条，来回横跳 | **分级反馈**——阻塞级 / 警告级 / 信息级，成功静默 |
| 8 | 上下文倾倒 | 大部分时间在检索和比对，真正动手很少 | **上下文预算**——筛选、分层、按需加载、压缩 |
| 9 | 上下文焦虑 | 前期仔细、后期敷衍，接近窗口上限时跳过验证 | **双层循环 + checkpoint + 内层预算** |
| 10 | 跨会话知识丢失 | 你已经裁决过的事，换个任务又冒出来 | **动态知识更新**——用户统筹、发现、决策 |
| 11 | 状态污染 | 一次性的执行数据被当成长期事实 | **状态分区**——草稿纸与持久状态分开，唯一主人 |
| 12 | 环境漂移 | 昨天能跑今天不行；"在我机器上没问题" | **环境锁定**——初始化脚本、lockfile、pin 住的 skill、间接层 |
| 13 | 模式复制漂移 | 新代码长得和你想淘汰的旧模式一模一样 | **模式基线化**——正向范例、会失败的架构检查、违规基线 |
| 14 | 技能触发不一致与体积失控 | 该触发的没触发；两个技能打架；技能越来越胖 | **description 写"何时用"**、四环节完整、先结构后行数 |

### 处方：8 组施工法

| 组 | 建成什么样 |
|---|---|
| 分层与渐进披露 | 入口文件只做路由，细节按需加载 |
| 前馈 ↔ 反馈配比 | 默认动作：把"必须 X"改写成"检查 X 是否成立" |
| 规则治理 | 带优先级、过期条件、状态位的登记表；矛盾检测持续发生 |
| skill 的写法 | description 是唯一常驻的竞争位；四环节完整；恰当的自由度 |
| 状态与跨会话 | 草稿纸与持久状态分开、唯一主人、checkpoint 必留的四项 |
| 环境锁定 | 确定性的初始化、pin 住的依赖与第三方 skill、外部服务的间接层 |
| 反馈分级 | 成功静默；阻塞级 / 警告级 / 信息级，把责任分界写清楚 |
| 范例优先于约定 | 正向范例、会失败的检查、违规基线、持续清理 |

## 怎么用

1. **体检。** 跑 [`SKILL.md` §3](skills/harness-engineering/SKILL.md) 的 20 条清单。它刻意做成可机检：目的是把"感觉 agent 不太行"变成"第 11 条在仓库里不成立"。把命中的条目记下来。
2. **诊断。** 拿命中的条目去 [`references/diagnoses.md`](skills/harness-engineering/references/diagnoses.md) 找对应病症。每条固定五段：症状 / 成因 / 判据 / 处方 / 常见误判。一次只处理最痛的一两处，别一次性重构全部。
3. **施工。** 通用做法在 [`references/playbook.md`](skills/harness-engineering/references/playbook.md)，八组，每组带"改造前 → 改造后"的形态对比。
4. **复检。** 回到第 1 步，确认没有引入新的坏味道——例如为治"虚假胜利"加了检查脚本，结果触发"反馈过载"。

## 为什么这么设计

两条决定贯穿全部内容：

- **反馈优先。** 想新增一条控制时，先写它的**可检查形式**，再考虑过程规则。检查落在循环的反馈环节，agent 每次都会走到；规则落在前馈环节，可能被一眼扫过。先写检查还会自然抑制指令膨胀。
- **确定性归代码，语义判断归模型。** 计数、日期推算、格式校验、字段完整性应该写成脚本；语气、理由是否充分、结论是否有支撑留给模型。大致上，可形式化的检查大头交给代码，剩下需要语义理解的部分交给模型。这是成本最优，不是风格偏好。

还有一条不太起眼但同样硬的要求：**每一轮只改一两处。** 这个 skill 里的几乎所有失效形态，都能用一组处方去治；一次性全上，会造出另一种失效形态。

## 如何给这个 skill 做增量补充

这个 skill 按"增量"成长，而不是靠重写。完整约定见 [`references/course-map.md`](skills/harness-engineering/references/course-map.md)，简要版：

1. **触发**——素材新增一讲、修订某讲，或答疑与实践复盘提出了新主张。
2. **判定**——它属于"新诊断"、"新处方"，还是"改写既有主张"。
3. **落位**——诊断进 `references/diagnoses.md`（沿用固定五段）；处方进 `references/playbook.md`（归入最接近的组，或新开一组并说明边界）；同时更新 `references/course-map.md` 的映射表。
4. **回链**——同步更新 `SKILL.md` §3/§4/§5 的索引。索引必须保持可解析：名字与路径能被 `grep` 到，链接能点开。
5. **留痕**——在 `references/course-map.md` 底部变更记录表追加一行。

纪律：只增不重排。既有条目编号是身份，不复用、不重排。被推翻的主张标 `superseded` 并保留，不删除。
